## 一、你现在要做的两步（都在商户平台，约 5 分钟）

### 第 1 步：开通「JSAPI 支付」产品权限 ⚠️ 当前阻塞点

**实测证据**（本机发真实请求到微信，不是推测）：

```
POST https://api.mch.weixin.qq.com/v3/pay/transactions/jsapi
→ HTTP 403  {"code":"NO_AUTH","message":"商户号该产品权限未开通，请前往商户平台>产品中心检查后重试"}
```

**怎么做**（官方《申请JSAPI支付权限指引》2025.07 版）：登录 [商户平台](https://pay.weixin.qq.com)
（**必须超级管理员**扫码）→ 顶部**「产品中心」** → 页面里**直接就有「JSAPI支付」这一项**
（与「APP支付」「H5支付」「Native支付」并列，**不用去「产品大全」里搜**）→ 点进去 → 点【**申请开通**】
→ 待审核（官方口径 **7 个工作日**内，实际多为当天~次日生效）。
官方链接：<https://pay.weixin.qq.com/doc/v3/merchant/4012791895>

> 官方原文：小程序支付与 JSAPI 支付**共用同一权限**，小程序场景只需申请 JSAPI 这一项。

**按路径仍然找不到，只有三种可能**：

| 可能 | 判据 | 处置 |
|---|---|---|
| 登录的**不是超管** | 「申请开通」按钮不显示/点不动 | 换**超级管理员**微信扫码登录（当初注册商户号、签协议那个号） |
| 入驻时**经营场景未勾「小程序」** | 产品中心**根本没有** JSAPI支付这一项，也无自助开通入口（微信社区同款案例：商户号 1665074027） | 只能走客服：商户平台右下角**在线客服**，或 **95017**（→ 微信支付 → 商户平台） |
| 旧版页面缓存 | 菜单叫法与文档不一致 | Ctrl+F5 强刷 / 退出重登 |

> 若列表里有这一项但状态是灰的，先做第 3 步（绑定 AppID）—— 两者互相依赖。

### 第 2 步：下载「微信支付公钥」

**实测证据**：

```
GET https://api.mch.weixin.qq.com/v3/certificates
→ HTTP 404  {"code":"RESOURCE_NOT_EXISTS",
   "message":"无可用的平台证书，请在商户平台-API安全申请使用微信支付公钥。"}
```

说明你的商户是**新版**（2024 年后微信不再签发平台证书，统一改用「微信支付公钥」）。
支付回调**必须验签**（否则任何人都能伪造回调把订单改成已支付），所以这个文件是**必需**的。

**怎么做**（官方《产品介绍-微信支付公钥》2026.05 版）：**超级管理员或安全联系人**登录商户平台
→ **账户中心 → API安全** → 找到**「微信支付公钥」**区块 → 点【**申请公钥**】→ 申请后**才会出现**
【**下载公钥**】按钮 → 得到 `pub_key.pem`（同页显示**公钥 ID**，形如 `PUB_KEY_ID_0112…`，一并记下）。
官方链接：<https://pay.weixin.qq.com/docs/merchant/products/update-pub-key/wxp-pub-key-guide.html>

> ⚠️ **最常见的卡点**：进到 API安全 页只看到「申请公钥」、看不到「下载公钥」—— 这是**正常的**，
> 微信要求**先申请再下载**。公钥**可重复下载**（与只给一次下载机会的商户 API 证书不同）。
> 若「微信支付公钥」区块**整个不显示** → 多半不是超管/安全联系人账号。

### 第 3 步：确认 AppID 绑定（双向）

| 在哪 | 做什么 |
|---|---|
| 商户平台 → **产品中心 → AppID账号管理** | 添加 `wx9dd757d2541bb6f4` |
| mp 后台 → **微信支付 → 关联商户号** | **确认**该绑定 |

**两边都做才算绑定成功**，只做一边下单会报 appid/mchid 不匹配。

### 拿到 `pub_key.pem` 后给我，我这边做的事（约 2 分钟）

```
scp pub_key.pem → /opt/lexy-mall/cert/pub_key.pem
.env 里取消注释 WX_PAY_PUBLIC_KEY_PATH=…/pub_key.pem
systemctl restart lexy-mall
node .tooling/check-wxpay.mjs --order     # 下单应变为成功
```

### 2.2 顺手修掉的一个**真实安全漏洞**

旧实现里回调验签只有一行 `return !HAS_WX_PAY` —— 意思是「**没配商户号就放行**」。
而 `POST /api/pay/notify` 是**公网开放**点位（`auth: false`）→ 任何人都能 POST 一个订单号
把订单标记成「已支付」，**白拿商品**。

**现在的口径**：沙箱模式 → **一律拒绝**（联调走 `/api/pay/mock-success`，需登录且走同一处理路径）；
真实模式 → 严格验签（三个判据：验签头齐备 / 时间戳 ±5 分钟防重放 / RSA-SHA256 通过），**任一不过即拒**。

线上实测（已生效）：

```

{"code":"FAIL","message":"未启用真实微信支付，支付回调已关闭（联调请用 /api/pay/mock-success）"}
```

## 三、代码实现说明（给以后维护的人）

### 3.1 为什么 `HAS_WX_PAY` 要「全有或全无」

只差公钥时会**整体回落沙箱**，这是刻意的：
若允许「下单能成、回调验不了」的半通状态 → **用户付了钱，订单还是待付款**，比明确走沙箱危险得多。

判定条件（五项缺一即 false）：`WX_MCH_ID` + 序列号 + **APIv3 密钥长度=32 字节** + 私钥可解析 + **公钥存在**。

### 3.2 三个踩过的坑（都已写进代码注释）

| 坑 | 现象 | 根因 |
|---|---|---|
| **`Accept-Language` 必须显式传** | 微信回 `406 传入了不支持的Accept-Language` | 不传时链路中间的设备会注入一个微信不认的值。**代码里已显式写死 `zh-CN`** |
| **`nonce` 必须按 base64 解码** | 解密恒失败，报 `Unsupported state or unable to authenticate data`（看着像密钥错） | 微信回调的 `resource.nonce` 是 **base64 字符串**；写成 `Buffer.from(iv)` 会按 utf8 取字节。**这个 bug 是被自测的加解密往返用例抓出来的** |
| **验签必须用原始 body** | 验签必然失败，且毫无线索 | `JSON.parse` 后再 `stringify` 会改变字节（键序/空格/转义）→ 新增 `rawBody` 机制 |

### 3.3 回调的三条硬约定

1. `rawBody: true` —— 签的是**微信发来的原始字节**
2. 应答体必须是 `{"code":"SUCCESS","message":"成功"}`（用 `rawHttp()`，不能套统一 `{code,msg,data}` 包装）
3. 失败必须回 **4xx/5xx** —— 微信只对非 2xx 才重试；回 200 等于「我处理完了」，订单会永远停在待付款

### 3.4 主动查单兜底

支付回调**异步且可能丢失**（部署重启、网络抖动、回调地址短暂 502）。
`POST /api/pay/query` 在「本地仍待付款 + 已启用真实支付」时会**主动向微信查一次**，
查到 `trade_state=SUCCESS` 就补齐订单状态 —— 避免「用户已扣款、订单显示待付款」。

> 「显式 0 → 关；**真实支付已启用 → 强制关**；显式 1 → 开；其余 → 非生产开」。
> 也就是说：**支付一旦接通，这个后门自己就关了**。

## 五、验收标准（不接受「配置看起来对」）

1. 真机 → 商品 → 下单 → **拉起收银台** → 实付最小金额
2. 支付成功页 → 订单状态变「待发货」
3. 商户平台「交易中心」能看到该笔流水
4. 服务器日志**无回调 403**；订单在**未手动干预**的情况下变已支付
5. 前端**不再出现**「模拟支付成功」按钮；直接 `POST /api/pay/mock-success` 应返回 **403**

## 六、排查手册（保留）

### 下单报错对照

| 微信返回 | 含义 | 处置 |
|---|---|---|
| `403 NO_AUTH 产品权限未开通` | 产品中心没开 JSAPI 支付 | 第一节第 1 步 |
| `APPID_MCHID_NOT_MATCH` / appid 相关 | AppID 与商户号未绑定 | 第一节第 3 步（**双向**） |
| `401 SIGN_ERROR` | 请求签名不对 | 检查序列号是否与证书一致、私钥是否配对 |
| `PARAM_ERROR out_trade_no` | 参数缺字段 | 代码问题（自测已覆盖） |

### 申请驳回高频原因（若将来需要重新申请）

1. **对公账户名 ≠ 主体名** —— 必须逐字等于「莱克电气绿能科技（苏州）有限公司」
2. **执照经营范围不含零售/销售** —— 缺就先去市监增经营范围
3. **主体类型/证件类型选错**（企业 vs 个体工商户）
4. **结算银行卡不是对公账户**，或开户行填错
5. 类目需资质（家用电器零售一般**不需要**，这也是选「商家自营」的原因）
